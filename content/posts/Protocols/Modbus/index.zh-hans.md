## Modbus是什么

Modbus 是一种应用于工业自动化领域的**主从式（Client/Server 或 Master/Slave）应用层通信协议**。它由莫迪康公司（Modicon，现施耐德电气旗下）于 1979 年为 PLC（可编程逻辑控制器）通信而发明。

由于其**开源、无版税、协议结构简单、极易部署**，Modbus 成为了工业控制系统中应用最广泛的通用“普通话”，主要用于解决不同厂商生产的设备之间的数据采集与控制互联问题。

本质是**读取与写入工业设备的寄存器数据**：

- **数据采集（监视）**： 上位机（如 SCADA、工控机、PLC）周期性向传感器、变送器、电表发出查询指令，读取当前的物理量（温度、压力、电压、电流等）。

- **控制下发（操作）**： 上位机向执行机构（如变频器、阀门控制器、继电器）写入控制信号，控制电机的启停、转速或阀门的开闭度。

## Modbus的种类

在了解 Modbus 的具体种类之前，必须先建立一个核心认知：**Modbus 的指令内容与底层传输方式是完全解耦的**。

Modbus 将报文严格拆分为两层：
* **PDU（Protocol Data Unit，协议数据单元）**：通信的**核心内容**，定义了“要做什么”。格式固定为：`功能码 (1B) + 数据段`。**PDU 是通用的，与具体的物理介质和传输网络完全无关。**
* **ADU（Application Data Unit，应用数据单元）**：**Modbus 应用层的完整报文**。它是用不同网络所特有的“外壳”（寻址、校验、报头），把通用的 PDU 包裹起来形成的。

```text
通用的 PDU 核心：
[ 功能码 (1B) ] + [ 数据 (Data) ]

具体的 ADU 完整帧：
[ 各种网络特有的外壳头部 ] + [ 通用 PDU ] + [ 校验尾部(若需要) ]
```

### Modbus RTU（最常见）

- 运行在串行总线（RS-485、RS-232）上。

- 数据以紧凑的二进制格式传输，末尾附带 16 位的 CRC 循环冗余校验码，传输效率高且抗干扰强。

```text
+---------------+---------------------+--------------------+
| 从机地址 (1B)   |     通用 PDU        |  CRC-16 校验 (2B)  |
+---------------+---------------------+--------------------+
|<----------------------- 完整 ADU ----------------------->|
```

### Modbus TCP

- 运行在标准工业以太网（TCP/IP，默认端口 502）上。

- 将 Modbus 报文直接封装进 TCP 载荷中（带有 MBAP 报头），由于 TCP 协议自带检验机制，去除了末尾的校验码。

```text
+------------------------+---------------------------------+
|     MBAP 报头 (7B)      |            通用 PDU             |
+------------------------+---------------------------------+
|<----------------------- 完整 ADU ----------------------->|
```

### Modbus ASCII

- 同样基于串口，但将每个字节拆解为两个可打印的 ASCII 字符传输，末尾使用 LRC 校验。易于人类阅读抓包，但传输开销翻倍，现已较少采用。

```text
+----------+---------------+----------------+----------+----------+
| 起始符(:) | 从机地址 (2B)  | 通用 PDU(字符)   | LRC (2B) | 结束符CRLF|
+----------+---------------+----------------+----------+----------+
|<----------------------- 完整 ADU ------------------------------>|
```

## PDU（协议数据单元）

### 核心数据模型

Modbus 把工业设备中的数据抽象为 4 种基本的内部存储区域：

| 数据类型             | 常见名称  |     位宽 | 访问权限 | 地址范围  | 典型用途          |
| ---------------- | ----- | -----: | ---- | ------- | ------------- |
| Coil             | 线圈    |  1 bit | 读/写  | `00001-09999` | 开关、继电器、启停控制   |
| Discrete Input   | 离散输入  |  1 bit | 只读   | `10001-19999` | 按钮、限位开关、数字量输入 |
| Input Register   | 输入寄存器 | 16 bit | 只读   | `30001-39999` | 传感器测量值        |
| Holding Register | 保持寄存器 | 16 bit | 读/写  | `40001-49999` | 参数、设定值、状态数据   |

Modbus 的核心数据模型是四个独立的逻辑地址空间：**两个 bit 地址空间（Coil、Discrete Input）和两个 16-bit Register 地址空间（Input Register、Holding Register）**。

```text
Modbus Device
│
├── Coils
│   ├── bit 0
│   ├── bit 1
│   └── ...
│
├── Discrete Inputs
│   ├── bit 0
│   ├── bit 1
│   └── ...
│
├── Input Registers
│   ├── register 0     16 bit
│   ├── register 1     16 bit
│   └── ...
│
└── Holding Registers
    ├── register 0     16 bit
    ├── register 1     16 bit
    └── ...
```

协议只定义如何访问这些数据，并不定义这些数据在业务上的具体含义。

举个例子：比如说让寄存器保存温度 `25.6°C`，有的厂商可能规定使用 `Holding Register 100 = 256`，实际温度 = `256 / 10 = 25.6 °C`，也可能规定使用 `Holding Register 100` 和 `Holding Register 101` 两个 16 位寄存器拼成一个 IEEE 754 `float`。Modbus 只提供地址空间和访问数据的方式。

### 功能码

功能码是 Modbus 协议中的**操作指令**，占 1 个字节（范围 0x01 ~ 0xFF）。它告诉从设备两件事：

- 操作四大区域中的哪一个？（Coil、Discrete Input、Input Register 还是 Holding Register）

- 是读操作还是写操作？（单点读、批量读、单点写、批量写）

由于每个功能码都直接与特定的数据模型和操作权限绑定，可以把功能码理解为针对设备寄存器的 **CRUD（增删改查）指令集**。

#### 八大常用功能码

| 功能码 (十六进制) | 功能码 (十进制) | 操作名称 | 目标数据区域 | 操作类型 | 操作粒度 / 单次上限 |
| :---: | :---: | :--- | :--- | :---: | :--- |
| **`0x01`** | `01` | Read Coils (读线圈) | 线圈 (Coils) | 读 | 批量 (1 ~ 2000 点) |
| **`0x02`** | `02` | Read Discrete Inputs (读离散输入) | 离散输入 (Discrete Inputs) | 读 | 批量 (1 ~ 2000 点) |
| **`0x03`** | `03` | Read Holding Registers (读保持寄存器) | 保持寄存器 (Holding Registers) | 读 | 批量 (1 ~ 125 个寄存器) |
| **`0x04`** | `04` | Read Input Registers (读输入寄存器) | 输入寄存器 (Input Registers) | 读 | 批量 (1 ~ 125 个寄存器) |
| **`0x05`** | `05` | Write Single Coil (写单个线圈) | 线圈 (Coils) | 写 | 单点 (`0xFF00` 为 ON，`0x0000` 为 OFF) |
| **`0x06`** | `06` | Write Single Register (写单个寄存器) | 保持寄存器 (Holding Registers) | 写 | 单个保持寄存器 (16-bit) |
| **`0x0F`** | `15` | Write Multiple Coils (写多个线圈) | 线圈 (Coils) | 写 | 批量 (1 ~ 1968 点) |
| **`0x10`** | `16` | Write Multiple Registers (写多个寄存器) | 保持寄存器 (Holding Registers) | 写 | 批量 (1 ~ 123 个寄存器) |

> **速记口诀：**
> * **1~4 全是读**：`01`、`02` 读 1-bit 开关量（线圈、离散输入）；`03`、`04` 读 16-bit 寄存器（保持、输入寄存器）。
> * **写操作看权限**：只有可读写的“线圈”和“保持寄存器”有写指令。`05`、`06` 写单点，`0F(15)`、`10(16)` 写连续多点。

### 数据段

PDU 格式固定为 `[ 功能码 (1B) ] + [ 数据段 (可变长，0~252B) ]`。

虽然功能码固定占 1 字节，但**数据段（Data）的具体格式并非千篇一律，而是完全依附于功能码的语义以及“当前是请求还是响应”**。

#### 1. 读操作 PDU 数据格式（以 03 读保持寄存器为例）

* **主站请求 PDU（Request）**：询问“从哪开始读？读几个？”
  * `03` (功能码 1B) + `起始地址 (2B)` + `寄存器数量 (2B)` $\to$ **固定 5 字节**。
  * *示例*：`03 00 00 00 02`（读取 0 号地址开始的 2 个寄存器）。
* **从站响应 PDU（Response）**：回答“一共几个字节？数值分别是多少？”
  * `03` (功能码 1B) + `字节计数 Byte Count (1B)` + `寄存器值列表 (N×2B)`。
  * *示例*：`03 04 00 19 00 0A`（返回 4 个字节，两个寄存器值分别为 `0x0019`、`0x000A`）。

#### 2. 写单个操作 PDU 数据格式（以 06 写单寄存器为例）

* **主站请求 PDU**：指定“往哪个寄存器写什么值？”
  * `06` (功能码 1B) + `目标地址 (2B)` + `写入值 (2B)` $\to$ **固定 5 字节**。
* **从站响应 PDU**：执行成功后**原样镜像返回**请求 PDU。
  * `06` + `目标地址 (2B)` + `写入值 (2B)` $\to$ **固定 5 字节**。

#### 3. 写多个操作 PDU 数据格式（以 10 写多寄存器为例）

* **主站请求 PDU**：
  * `10` (功能码 1B) + `起始地址 (2B)` + `寄存器数量 (2B)` + `写入字节数 (1B)` + `数值列表 (N×2B)`。
* **从站响应 PDU**：执行成功后确认写入范围。
  * `10` (功能码 1B) + `起始地址 (2B)` + `寄存器数量 (2B)` $\to$ **固定 5 字节**。

### 异常响应机制

如果主站发出了错误的指令（例如请求了一个不存在的寄存器地址，或者写入的值超限），从站不会直接宕机，而是会生成一个**异常响应 PDU（固定 2 字节）**：

```text
+-----------------------+-----------------------+
|  异常功能码 (1 字节)    |    异常码 (1 字节)      |
| (请求功能码 + 0x80)     |    (Exception Code)   |
+-----------------------+-----------------------+
```

1. **异常功能码（1 字节）**：
   - 规律是把原请求功能码的最高位（Bit 7）置 `1`，即：**原请求功能码 + `0x80`**。
   - 主站收到回复后，只要看到功能码 $\ge \text{0x80}$，就能立刻判定这是一条“报错回复”。
   - *示例*：发的是 `0x03`（读保持寄存器），报错时返回 `0x83`；发的是 `0x06`（写单寄存器），报错时返回 `0x86`。

2. **异常码（Exception Code，1 字节）**：
   - 紧跟在异常功能码后面，标明具体的出错原因。

#### 常见异常码

| 异常码 (Hex) | 异常名称 | 产生原因 |
| :---: | :--- | :--- |
| **`0x01`** | 非法功能码 (Illegal Function) | 从站不支持这个功能码，或者当前状态下不允许执行该操作。 |
| **`0x02`** | 非法数据地址 (Illegal Data Address) | 访问的寄存器起始地址不存在，或者 `起始地址 + 请求数量` 超出了设备上限。 |
| **`0x03`** | 非法数据值 (Illegal Data Value) | 请求中附带的数据不合法（例如单次请求读取的寄存器数量为 0 或超限，写入的数值越界等）。 |
| **`0x04`** | 从站设备故障 (Slave Device Failure) | 从站内部发生不可恢复的硬件或软件错误，无法执行请求。 |

## ADU（应用数据单元）

### Modbus RTU

#### 帧结构

```text
+---------------+---------------+-----------------------+-------------------+
| 从机地址 (1B)  |  功能码 (1B)   |     数据段 (可变长)     |  CRC-16 校验 (2B)  |
+---------------+---------------+-----------------------+-------------------+
|               |<----------------- PDU --------------->|                   |
|<--------------------------------- ADU ----------------------------------->|
```

- **从机地址 (1 字节)**

  - `0`：广播地址（所有从站执行但不回送响应）。

  - `1 ~ 247`：独立从站地址（只有匹配的从站才响应，其余静默丢弃）。

  - `248 ~ 255`：保留地址。

- **CRC-16 校验 (2 字节)**

  - 覆盖从“从机地址”到“数据段结束”的所有字节。

  - 采用 **CRC-16/MODBUS** 规范（多项式 `0xA001`，初始值 `0xFFFF`）。

  - **大小端陷阱**：与 PDU 数据段的大端序相反，CRC-16 校验在传输时严格采用**低字节在前，高字节在后（Little-Endian）**。

- **隐式帧分界（3.5T 与 1.5T 机制）**

  - **3.5T 判帧结束**：总线在数据帧之间必须维持至少 **3.5 个字符时间（3.5T）** 的物理静默。检测到 3.5T 的空闲即可判定上一帧接收完毕。

  - **1.5T 判定坏帧**：一帧内部相邻字符之间的间隔不得超过 **1.5 个字符时间（1.5T）**，超过则判定为断流错帧并丢弃。

#### CRC-16 计算步骤

1. **预置寄存器**：定义一个 16 位的 CRC 寄存器，初始值赋值为 `0xFFFF`。

2. **异或首字节**：取报文的第 1 个字节（8 位），与 CRC 寄存器的**低 8 位**进行异或运算，高 8 位保持不变。

3. **循环移位 8 次**（对该字节的每一位进行处理）：

   - 检查 CRC 寄存器的**最低有效位（LSB，即最右边的 Bit 0）**：

     - **如果 LSB 是 1**：将 CRC 寄存器**右移 1 位**，最高位补 0，然后与多项式 `0xA001` 进行异或。

     - **如果 LSB 是 0**：仅将 CRC 寄存器**右移 1 位**，最高位补 0，不进行异或。

   - 重复上述判断与移位，共执行 **8 次**。至此，该字节处理完毕。

4. **处理下一字节**：取出报文的下一个字节，与当前 CRC 寄存器的低 8 位异或，重复步骤 3。

5. **遍历完成**：直到报文内所有字节（从设备地址到数据段最后一个字节）均处理完毕。

6. **最终结果与打包**：此时 CRC 寄存器内的 16 位数值即为最终校验码。

   - 设算出的结果为 `0xHILO`（高字节为 `HI`，低字节为 `LO`）。

   - **追加到报文末尾时，必须先发 `LO`（低字节），再发 `HI`（高字节）**。

### Modbus TCP

Modbus TCP 运行在 TCP/IP 协议栈（默认端口 502）。由于 TCP 具备可靠传输和校验重传机制，Modbus TCP **移除了末尾的 CRC 校验**，改为在头部增加 7 字节的 **MBAP（Modbus Application Protocol）报头**。

#### 帧结构

```text
+-------------------------------+---------------+-----------------------+
|         MBAP 报头 (7B)         |  功能码 (1B)   |     数据段 (可变长)     |
+-------------------------------+---------------+-----------------------+
|                               |<----------------- PDU --------------->|
|<--------------------------------- ADU -------------------------------->|
```

#### MBAP 报头

```text
+-----------------------+-----------------------+---------------+---------------+
| 事务元标识符 (2 字节)    |  协议标识符 (2 字节)    |  长度 (2 字节) | 单元标识符(1B)  |
|   (Transaction ID)    |     (Protocol ID)     |    (Length)   |   (Unit ID)   |
+-----------------------+-----------------------+---------------+---------------+
```

MBAP 报头共占 **7 字节**，报头内部所有 16 位整型字段均严格遵循**网络字节序（大端序，高字节在前）**。

- **事务元标识符（Transaction ID，2 字节）**：请求与响应的事务序号配对。主站发送时可自增生成，从站响应时原样回传，支持 TCP 长连接下的异步并发请求。

- **协议标识符（Protocol ID，2 字节）**：标识上层协议类型，Modbus 协议固定恒为 `0x0000`。

- **长度（Length，2 字节）**：标明紧随此字段之后的总字节数（等于 `1 字节 Unit ID + PDU 长度`），用于解决 TCP 流式传输的粘包与分包问题。

- **单元标识符（Unit ID，1 字节）**：相当于串口模式下的从机地址。网关模式下用于寻址下挂的 RS-485 设备；纯 TCP 直连设备时常填 `0x01` 或 `0xFF`。

### Modbus ASCII

基于串口通信，将二进制字节转换为 2 个可打印的 ASCII 字符传输。

#### 帧结构

```text
+----------+---------------+---------------+-------------------+----------+----------+
| 起始符(:) | 从机地址 (2B)  |  功能码 (2B)   |   数据段 (可变长)   | LRC (2B) | 结束符CRLF|
+----------+---------------+---------------+-------------------+----------+----------+
|          |               |<------------- PDU(ASCII) -------->|          |          |
|<------------------------------------ ADU ----------------------------------------->|
```

- **起始与结束**：以冒号 `:`（`0x3A`）作为帧头，以回车换行符 `CR LF`（`0x0D 0x0A`）作为帧尾。

- **校验算法**：采用 **LRC（Longitudinal Redundancy Check，纵向冗余校验）**，结果转化为 2 个 ASCII 字符。

- **特点**：不需要精确的定时器测算 3.5T，抓包可读性好；但报文长度翻倍，传输效率极低。

#### LRC 计算步骤

计算范围包含从 **从机地址** 到 **数据段最后一个字节**（注意：**不包含**起始符 `:` 和结束符 `\r\n`，且参与计算的是**原始二进制数值**，而不是转换后的 ASCII 字符）。

1. **累加求和**：将报文中所有待校验的字节（8 位）直接相加。

2. **丢弃溢出**：累加过程按 8 位无符号整数进行，超出 255（`0xFF`）的进位全部丢弃。

3. **求补码（取反加一）**：对保留下的 8 位累加和进行求补运算。

4. **转为 ASCII 字符**：将最终算出的这 1 字节 LRC 十六进制数值，拆成 2 个 ASCII 字符放入报文尾部。
